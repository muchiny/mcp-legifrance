# 09 — Le SDK Rust `rmcp` supporte-t-il MCP 2026-07-28 (« MCP v2 ») ?

Date de la recherche : 2026-10-15. Axe : choix du SDK pour l'adapter entrant MCP (`lf-adapter-mcp`) du serveur Légifrance en Rust.

## 0. Verdict

**Oui. `rmcp` 3.5.1 (publié le 2026-10-05) implémente la révision 2026-07-28.** Il sert aussi les clients plus anciens (2025-11-25 et antérieurs) dans le même binaire, en stdio comme en Streamable HTTP. La révision 2026-07-28 est bien la plus récente : aucune révision ni RC plus récente n'existe au 2026-10-15.

- Le support date de la ligne 3.x : 3.0.0 a été publié le 2026-07-28, le jour même de la GA. Mais `ProtocolVersion::LATEST` n'est passé à `2026-07-28` qu'en 3.5.0, le 2026-09-27.
- Le SDK Rust est **Tier 1** sur la page officielle des SDK depuis le 2026-08-21. Le billet de GA du 2026-07-28 le présentait encore comme « supports the new spec in beta ».
- Recommandation : option (a). Adopter `rmcp ~3.5.1` avec les features par défaut plus `transport-io`, et déclarer explicitement les versions de protocole supportées. Il faut quand même confiner `rmcp` dans `lf-adapter-mcp`, parce que l'API du SDK change vite : 0.17, puis 1.0, 2.0 et 3.0 entre février et juillet 2026.
- Ne **pas** écrire notre propre couche protocolaire. Le squelette exact est en §8.

Règles de compatibilité utiles pour nous :
- Un serveur **dual-era** choisit son comportement selon la façon dont le client ouvre la conversation : `_meta` moderne → traitement sans état, `initialize` → sémantique legacy. Voir `SPEC:docs/specification/2026-07-28/basic/versioning.mdx:174-183`.
- Matrice des combinaisons client/serveur : `versioning.mdx:164-172`. Un client **legacy** face à un serveur **modern-only** échoue (`:170`). Il **faut** donc rester dual-era pour les clients 2025-11-25.
- En stdio, un client dual-era sonde avec `server/discover`, puis se replie sur `initialize` en cas d'erreur non moderne (`versioning.mdx:136-138`).

### 3.3 Cycle de vie : `initialize` (legacy) et `server/discover` / `_meta` (modern), en stdio
- `RS:crates/rmcp/src/service/server.rs:573-690` contient la boucle de démarrage de `serve_server`, celle qu'utilise `.serve(stdio())` :
  - `ping` avant l'init → réponse vide.
  - `InitializeRequest` → cycle de vie **legacy** (`:600`).
  - `DiscoverRequest` → réponse « bootstrap » sans choisir d'ère (`:625-646`).
  - Toute autre requête portant un `_meta` complet → cycle de vie **modern**, avec `peer.require_request_metadata()` (`:668`).
  - Une version demandée hors de `supported_protocol_versions` reçoit `UnsupportedProtocolVersion` (`:648-666`).
- La négociation d'`initialize` suit `negotiate_protocol_version` (`service/server.rs:486-523`). Si le client demande une version sans handshake, ou une version non supportée, le serveur répond avec la plus récente version **à handshake** qu'il supporte, c'est-à-dire 2025-11-25.
- Dans `ServerHandler` (`RS:crates/rmcp/src/handler/server.rs`) :
  - `negotiate_initialize` : `:365-376`.
  - `supported_protocol_versions()` : `:388-390`. Par défaut, elle renvoie **tous** les `KNOWN_VERSIONS`.
  - `discover()` : `:392-400`. Le défaut est `DiscoverResult::from_server_info(...)`.
- Dans le dispatch `handle_request` (`handler/server.rs:51-271`) :
  - Contrôle de version inline : `:63-72`.
  - Clés `_meta` obligatoires pour 2026-07-28 (`:79-99`). La liste figure dans `RS:crates/rmcp/src/model/meta.rs:399-403` (`DRAFT_REQUIRED_KEYS`) : `io.modelcontextprotocol/protocolVersion` et `io.modelcontextprotocol/clientCapabilities`.
  - `ping` refusé en ère modern : `:111-117`.
  - `resources/subscribe` legacy uniquement, `subscriptions/listen` modern uniquement : `:147-200`.
  - `InputRequiredResult` (MRTR) interdit pour les pairs < 2026-07-28 : `:246-251`.
  - **Remplissage automatique des cache hints** pour les pairs ≥ 2026-07-28, et suppression de `resultType` pour les pairs legacy : `:252-259`.
  - Erreur `RESOURCE_NOT_FOUND` réécrite en `INVALID_PARAMS` (`-32602`) pour les pairs ≥ 2026-07-28 : `:264-270`.
- Codes d'erreur alignés sur la spec : `UNSUPPORTED_PROTOCOL_VERSION = -32022`, `MISSING_REQUIRED_CLIENT_CAPABILITY = -32021`, `HEADER_MISMATCH = -32020` (`RS:crates/rmcp/src/model.rs:623-626`). Ils correspondent à `SPEC:docs/specification/2026-07-28/changelog.mdx:61-67`.

### 3.4 Sessions et transport Streamable HTTP
- Une requête 2026-07-28 est **toujours** servie sans état : pas de `Mcp-Session-Id`, pas de GET/DELETE, pas de `Last-Event-ID`. L'option `legacy_session_mode` (ex-`stateful_mode`) ne concerne que les versions < 2026-07-28. Voir `RS:README.md:1527-1575` et `CHANGELOG.md:259` (#999) ainsi que la section « Changed » de 3.0.0-beta.1.
- `with_stateless_protocol_metadata_required(true)` sert aux serveurs modern-only (`README.md:1568-1574`).
- En-têtes standard SEP-2243 (`Mcp-Method`, `Mcp-Name`, `Mcp-Param-*` via `x-mcp-header`) : émis et validés automatiquement (`README.md:1489-1525`). Cela ne concerne que HTTP, pas notre transport stdio par défaut.

## 5. Pièges : la documentation contredit parfois le code de 3.5.1

1. `RS:README.md:395-399` montre `read_resource` renvoyant `Result<ReadResourceResult, McpError>`. Or le trait exige `Result<ReadResourceResponse, McpError>` (`RS:crates/rmcp/src/handler/server.rs:445-453`). Il faut écrire `Ok(result.into())`, comme le fait `RS:examples/servers/src/common/counter.rs:240-245`.
2. `RS:README.md:385-391` construit `ListResourcesResult { resources, next_cursor: None, meta: None }`. Le struct a aussi `result_type`, `ttl_ms` et `cache_scope` (macro `paginated_result!`, `model.rs:1729-1772`, instanciée en `:1817`), donc ce littéral ne compile pas. Il faut passer par `ListResourcesResult::with_all_items(..)` ou utiliser `..Default::default()`.
3. `RS:examples/servers/src/completion_stdio.rs:422-436` écrit sur **stdout** avec `println!` dans un serveur stdio. À ne pas copier : tous les logs doivent aller sur **stderr** (`counter_stdio.rs:10-14`).
4. Les arguments de prompt sont des `Record<string,string>` côté spec. Les champs non `String` doivent tolérer la forme chaîne (`RS:examples/servers/src/common/counter.rs:30-47`).
5. `ServerInfo` est déprécié au profit de `ServerConfig` depuis 3.4.0 (`model.rs:1178, 1200-1206` ; `CHANGELOG.md:56`).
6. `Reference`, `Tool`, `ResourceTemplate`, `ReadResourceResult` et `InitializeResult` sont `#[non_exhaustive]`. Il faut utiliser les constructeurs `new` / `with_*` et des `match` avec `_ =>`.
7. Le SDK ne vérifie pas que le `#[derive(JsonSchema)]` des paramètres produit un schéma `type: object`. Une erreur déclenche un `panic!` à la construction du routeur (`rmcp-macros/src/tool.rs:200-208`). Il faut un test unitaire qui appelle `tool_router()`.

## 7. Options pour notre plan

### (a) `rmcp` supporte déjà 2026-07-28 : **c'est notre cas**
- Version : `rmcp = "~3.5.1"`, ce qui autorise les correctifs 3.5.x et pas 3.6. Committer `Cargo.lock`. Passer en 3.6 sera une décision explicite, après lecture du CHANGELOG, à cause du précédent `LATEST` changé en mineure.
- Features : les features par défaut (`base64`, `macros`, `server`) plus **`transport-io`**, indispensable pour `stdio()` (`RS:crates/rmcp/src/transport.rs:91-94` ; la feature n'est pas dans `default`, voir l'index). Ajouter `transport-streamable-http-server` plus tard pour HTTP. **Ne pas** activer `request-state`, `elicitation` ni `auth` : pas de MRTR et pas d'OAuth en lecture seule stdio.
- Ajouter `schemars = "1"` en dépendance directe : la dérivation `JsonSchema` en a besoin, comme dans `RS:examples/servers/Cargo.toml` où `schemars = "1.0"` est déclaré directement. Garder la même majeure que `rmcp`, qui dépend de `schemars ^1.0`.
- MSRV : Rust ≥ 1.88, édition 2024 côté `rmcp`.
- **Façade quand même** : seul `lf-adapter-mcp` dépend de `rmcp`. Les types du domaine et de l'application ne doivent jamais exposer de types `rmcp::model::*`. Les DTO MCP (paramètres et sorties `JsonSchema`) vivent dans l'adapter, avec des `From`/`TryFrom` vers les types du domaine. Raison : l'API a changé de majeure trois fois en cinq mois (1.0 le 2026-03-03, 2.0 le 2026-06-29, 3.0 le 2026-07-28).
- Fixer explicitement `supported_protocol_versions` au lieu de dépendre de `KNOWN_VERSIONS`. Recommandation : `[2025-06-18, 2025-11-25, 2026-07-28]`, parce que `outputSchema`/`structuredContent` existent depuis 2025-06-18. C'est à valider contre nos clients cibles (cf. questions ouvertes).

### (b) Support partiel ou absent : **n'est pas notre cas**, gardé comme repli
- Si un défaut bloquant apparaît, l'ordre des recours est :
  1. Épingler la dernière 3.x saine.
  2. Contourner dans l'adapter, par exemple en surchargeant `list_tools` ou `discover`, ou en encapsulant les sorties (#1337).
  3. Contribuer en amont : le dépôt a des SLA Tier 1 de triage, voir `RS:ROADMAP.md:17-18`.
  4. Basculer vers `pmcp` derrière la même façade.
- **Écrire notre propre couche 2026-07-28** n'est pas recommandé. Estimation (NON VÉRIFIÉE, ordre de grandeur) pour un serveur **stdio seul**, dual-era, limité à outils, resources et templates, prompts, completions et discover : de 2 500 à 4 000 lignes de Rust plus les tests. Points de comparaison :
  - le schéma TS 2026-07-28 fait 3 197 lignes (`SPEC:schema/2026-07-28/schema.ts`) ;
  - `rmcp/src` fait 51 526 lignes au total, dont `model.rs` (5 608), `meta.rs` (859), `service/server.rs` (1 444) et `handler/server.rs` (873) ;
  - `rmcp-macros/src` fait 1 790 lignes et `rmcp` compte 90 fichiers de tests.

  Les risques :
  - **La conformité.** Il faudrait gérer la matrice legacy/modern, les règles sur `_meta`, `resultType`, les cache hints, les codes d'erreur et le repli `initialize`, puis passer `@modelcontextprotocol/conformance`.
  - **La maintenance** à chaque révision de la spec.
  - **L'absence des macros de schéma.**

  À n'envisager que si `rmcp` disparaissait ou devenait incompatible.

### Compatibilité avec les clients 2025-11-25
Elle est automatique avec `rmcp` 3.5.1 :
- Un client legacy envoie `initialize` et reçoit `protocolVersion` négociée, au plus 2025-11-25 (`service/server.rs:486-523`).
- Un client moderne envoie `server/discover` ou appelle directement avec `_meta` (`service/server.rs:573-690`).
- Les formes de résultat sont adaptées par version (`handler/server.rs:246-270`).

Il nous reste à tester les deux ères en CI, en rejouant des requêtes JSON-RPC brutes sur le binaire stdio.
