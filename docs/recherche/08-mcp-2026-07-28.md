## 1. Résumé exécutif

1. **« MCP v2 » = révision `2026-07-28`, c'est bien la dernière.** Le dépôt de la spec marque `2026-07-28` comme « latest » (`[S] docs/docs.json:33`, `:411`), la page de versioning la déclare **Current** (`[S] docs/docs/2026-07-28/learn/versioning.mdx:27`), la constante du schéma vaut `LATEST_PROTOCOL_VERSION = "2026-07-28"` (`SCHEMA:30`). Les tags du dépôt s'arrêtent à `2026-07-28` et `2026-07-28-RC` (`git ls-remote --tags`, voir §2). Le `draft` actuel est identique à `2026-07-28` aux liens près, et son changelog est vide : « Changes since the most recent release will accumulate here. » (`[S] docs/specification/draft/changelog.mdx`). **Aucune révision ni RC postérieure n'existe au 2026-10-15.**
   - Le terme « v2 » n'apparaît pas dans la spec. Il vient des SDK (TypeScript v2, Python `mcp` v2, C# 2.0, rmcp 3.x), du « v2 runtime » de Claude Code, et de l'URL de l'article Cloudflare. La spec dit **« modern »** pour 2026-07-28 et suivantes, **« legacy »** pour 2025-11-25 et avant (`SPEC/basic/versioning.mdx:29-39`).
2. **Rupture majeure : le protocole devient sans état.** Plus de `initialize`/`notifications/initialized`, plus de `Mcp-Session-Id`. Chaque requête porte sa version et les capacités du client dans `params._meta` (`SPEC/changelog.mdx:12-14`). Le serveur **DOIT** implémenter `server/discover` (`SPEC/changelog.mdx:16`, `SPEC/server/discover.mdx:7-9`).
3. **Tous les résultats portent `resultType`** (`"complete"` pour nous) (`SPEC/changelog.mdx:26`, `SCHEMA:223-236`). Les résultats `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list`, `resources/read` et `server/discover` **DOIVENT** porter `ttlMs` et `cacheScope` (`SPEC/server/utilities/caching.mdx:13-21`).
4. **Le serveur n'émet plus jamais de requête JSON-RPC.** L'élicitation, le sampling et les roots passent par MRTR (`InputRequiredResult`) (`SPEC/changelog.mdx:24`, `SPEC/basic/transports/stdio.mdx:55`). Un serveur Légifrance en lecture seule **n'a pas besoin de MRTR**.
5. **Retrait et dépréciation.** Sont retirés : `ping`, `logging/setLevel`, `resources/subscribe` et `resources/unsubscribe` (remplacés par `subscriptions/listen`), `notifications/roots/list_changed`, la reprise SSE (`Last-Event-ID`) et `notifications/elicitation/complete`. Sont dépréciés : **Logging, Sampling, Roots**, le DCR et HTTP+SSE (`SPEC/changelog.mdx:18-28`, `:53-60`, `:73-99`).
6. **La compatibilité est indispensable aujourd'hui.** VS Code (`main` au 2026-10-15) n'envoie encore que `initialize` en `2025-11-25` (`[VS] src/vs/platform/mcp/common/modelContextProtocol.ts:43`, `src/vs/workbench/contrib/mcp/common/mcpServerRequestHandler.ts:113-116`). Pour Cursor, la seule trace trouvée est un rapport de bug selon lequel il n'utilise que `initialize` (**NON VÉRIFIÉ**, §11). Claude Code, à l'inverse, sonde `server/discover` par défaut sur stdio depuis la 2.1.292 (`[CC] CHANGELOG.md:652`). **Notre serveur doit donc être « dual-era »** : il sert les requêtes modernes sans état et répond aussi à `initialize` pour les clients legacy. La spec l'autorise (« MAY ») (`SPEC/basic/versioning.mdx:126-130`, `:174-183`).

## 4. Cycle de vie sans session

### 4.1 Ce qui remplace `initialize`

- « There is no negotiation handshake. Every request carries its protocol version, and the server accepts or rejects each request independently » (`SPEC/basic/versioning.mdx:12-13`).
- `RequestParams._meta` est **requis** dans le type (`SCHEMA:179-181`). Clés par requête (`SPEC/basic/index.mdx:373-378`, `SCHEMA:63-111`) :

| Clé `_meta` | Type | Requis | Rôle |
|---|---|---|---|
| `io.modelcontextprotocol/protocolVersion` | string | **Oui** | version de la requête (`"2026-07-28"`) |
| `io.modelcontextprotocol/clientCapabilities` | `ClientCapabilities` | **Oui** (`{}` = aucune capacité optionnelle) | capacités du client pour cette requête |
| `io.modelcontextprotocol/clientInfo` | `Implementation` | Non (client SHOULD) | identité du client, uniquement pour affichage et logs |
| `io.modelcontextprotocol/logLevel` | `LoggingLevel` | Non (déprécié) | active `notifications/message` pour cette requête |
| `progressToken` | string \| int | Non | active `notifications/progress` |

- Requête sans champ requis : « malformed; the server **MUST** reject it with JSON-RPC error code `-32602` (Invalid params). On HTTP, the response status **MUST** be `400 Bad Request`. » (`SPEC/basic/index.mdx:380-382`). D'après la suite de conformance, le serveur **ne doit pas exiger** `clientInfo` (`[CF] src/scenarios/server/stateless.ts:37-39`).
- Capacité client manquante : « the server **MUST** return a `MissingRequiredClientCapabilityError` (`-32021`) whose `data.requiredCapabilities` lists the missing capabilities. On HTTP … `400` » (`SPEC/basic/index.mdx:387-392`). `requiredCapabilities` est un **objet `ClientCapabilities`**, pas un tableau (`SCHEMA:513-526` ; `[CF] src/scenarios/server/stateless.ts:44-45`). Notre serveur n'exige aucune capacité client, donc ce cas ne se présente pas.
- Identité du serveur : « Servers **SHOULD** include … `io.modelcontextprotocol/serverInfo` in every result's `_meta` » (`SPEC/basic/index.mdx:396-402`, `SCHEMA:143-158`). `clientInfo` et `serverInfo` sont auto-déclarés : ils ne servent ni à changer le comportement ni à prendre des décisions de sécurité (`SPEC/basic/index.mdx:404-410`).

### 4.2 Négociation de version

- Version dans `_meta`, et **aussi** dans l'en-tête `MCP-Protocol-Version` en HTTP (`SPEC/basic/versioning.mdx:41-46`).
- Version non implémentée : « it **MUST** respond with an `UnsupportedProtocolVersionError` listing the versions it does support » (`SPEC/basic/versioning.mdx:48-66`). Forme exacte (`SCHEMA:483-501`) :

```json
{"jsonrpc":"2.0","id":1,"error":{"code":-32022,"message":"Unsupported protocol version",
 "data":{"supported":["2026-07-28","2025-11-25"],"requested":"1900-01-01"}}}
```

- Le client SHOULD choisir une version commune et réessayer (`SPEC/basic/versioning.mdx:69-71`). L'appel à `server/discover` est **facultatif** pour le client (`:73-78`).
- Statelessness, règles serveur (`SPEC/basic/index.mdx:182-209`) : le serveur MUST NOT déduire le contexte (capacités, version, identité) des requêtes précédentes sur la même connexion (`:191-193`). Il SHOULD gérer des requêtes issues de plusieurs conversations sur le même processus (`:194-195`). Tout état qui couvre plusieurs requêtes MUST passer par un identifiant explicite (`:200-202`). La note `:204-209` précise qu'un processus stdio n'est **pas** une session.

### 4.3 `server/discover` : forme exacte

Requête (`SPEC/server/discover.mdx:13-31` ; `SCHEMA:665-668`, `params: RequestParams`, donc `_meta` seul) :

```json
{"jsonrpc":"2.0","id":"discover-1","method":"server/discover",
 "params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28",
   "io.modelcontextprotocol/clientInfo":{"name":"ExampleClient","version":"1.0.0"},
   "io.modelcontextprotocol/clientCapabilities":{}}}}
```

Réponse (`SPEC/server/discover.mdx:38-59` ; `SCHEMA:678-697`, `DiscoverResult extends CacheableResult`) :

```json
{"jsonrpc":"2.0","id":"discover-1","result":{
  "resultType":"complete",
  "supportedVersions":["2026-07-28"],
  "capabilities":{"tools":{},"resources":{}},
  "_meta":{"io.modelcontextprotocol/serverInfo":{"name":"ExampleServer","version":"1.0.0"}},
  "instructions":"This server provides weather and resource utilities.",
  "ttlMs":3600000,"cacheScope":"public"}}
```

- Champs : `supportedVersions` (requis), `capabilities` (requis), `instructions` (optionnel), `ttlMs` et `cacheScope` (**requis** par `CacheableResult`), `_meta.serverInfo` (SHOULD) (`SPEC/server/discover.mdx:94-101`).
- `serverInfo` est passé du corps de `DiscoverResult` vers `_meta` après la finalisation de SEP-2575 (PR #3002) (`[S] seps/2575-stateless-mcp.md:789-798`). Les articles ou exemples antérieurs qui montrent `result.serverInfo` sont donc périmés.
- Usages prévus : présenter le serveur, et servir de sonde de rétrocompatibilité sur stdio (`SPEC/server/discover.mdx:62-81`).

### 4.4 Capacités du serveur

`ServerCapabilities` (`SCHEMA:793-883`) : `experimental`, `logging` (déprécié), `completions`, `prompts{listChanged}`, `resources{subscribe,listChanged}`, `tools{listChanged}`, `extensions`. Elles ne sont déclarées **que dans `DiscoverResult`** en mode moderne (`SPEC/server/prompts.mdx:41-42`), et dans `InitializeResult` en mode legacy.

Pour nous : `{"tools":{}, "resources":{}, "prompts":{}, "completions":{}}`. Pas de `listChanged`, pas de `subscribe`, pas de `logging`.

### 4.5 Instructions du serveur

- En mode moderne, `instructions` existe **uniquement** dans `DiscoverResult` (`SCHEMA:689-696`). Le texte décrit le serveur et aide le modèle, sans dupliquer les descriptions des tools.
- En mode legacy, il reste dans `InitializeResult` (révision 2025-11-25).
- Contrainte pratique côté client : Claude Code tronque les instructions serveur au-delà de **4 096 caractères** (« Server instructions, and the description of a tool that loads upfront: 4,096 characters »), d'après https://code.claude.com/docs/en/mcp (lu par WebFetch le 2026-10-15). Viser moins de 2 000 caractères, l'essentiel en tête.

### 4.6 Rétrocompatibilité avec les clients legacy

- « A server that wishes to support both legacy clients … and modern clients … **MAY** implement both behaviors. » (`SPEC/basic/versioning.mdx:126-130`).
- Un serveur **modern-only** « **SHOULD** name the protocol versions it supports in any error it returns to an `initialize` request » (`:154-157`).
- Choix de l'ère par un serveur dual-era (`:174-183`) :
  - une requête qui porte le `_meta` moderne est servie **sans état** selon 2026-07-28 ;
  - une requête `initialize` sélectionne la sémantique legacy, **limitée au processus stdio** ou à la session HTTP ;
  - « A dual-era server **MAY** serve both eras concurrently on the same endpoint or process. »
- Matrice de compatibilité (`:159-172`) : un client legacy face à un serveur modern-only **échoue** (« Legacy clients have no fall-forward mechanism ») ; un client legacy face à un serveur dual-era fonctionne.
- Côté client, sur stdio : sonder avec `server/discover`. Un `DiscoverResult` ou une erreur moderne reconnue indique un serveur moderne. Toute autre erreur, ou un silence, déclenche le repli sur `initialize`. Le repli « **MUST NOT** be keyed to one specific error code » (`SPEC/basic/transports/stdio.mdx:121-147`).
- **Piège de conformance.** Le scénario `server-stateless` envoie `initialize`, `ping`, `logging/setLevel`, `resources/subscribe` et `resources/unsubscribe` **avec un `_meta` moderne valide**, et attend HTTP 404 avec `-32601` (`[CF] src/scenarios/server/stateless.ts:815-849`). Un serveur dual-era doit donc distinguer :
  - `initialize` **sans** `_meta` moderne (forme legacy : `params.protocolVersion`, `params.capabilities`, `params.clientInfo`) → handshake legacy ;
  - `initialize` **avec** `_meta["io.modelcontextprotocol/protocolVersion"] = "2026-07-28"` → méthode inconnue (`-32601`, 404 en HTTP).
- Précédent SDK : la logique de rmcp suit cette distinction. `uses_inline_negotiation = !matches!(request, InitializeRequest)`, et les métadonnées modernes ne sont exigées que pour `server/discover`, sur une connexion ouverte sans `initialize`, ou pour une requête qui déclare 2026-07-28 ou plus (`[RS] crates/rmcp/src/handler/server.rs:57-96`).

## 5. Transports

### 5.1 stdio

Règles conservées ou précisées (`SPEC/basic/transports/stdio.mdx`) :

- Un message JSON-RPC par ligne, sans retour à la ligne interne (`:10-14`). Pas de batch (§3.4).
- `stderr` libre pour les logs ; le client ne doit pas l'interpréter comme une erreur (`:14-17`). Le serveur **MUST NOT** écrire autre chose que des messages MCP valides sur stdout (`:18-19`).
- **Nouveau : le serveur MUST NOT écrire de *requêtes* JSON-RPC sur stdout** (`:55`). Il n'écrit que des réponses, des notifications liées à une requête en cours (progress, message) et des notifications de `subscriptions/listen` étiquetées par `subscriptionId` (`:39-53`).
- Métadonnées entièrement dans le corps, sans couche d'en-têtes (`:65-72`).
- Annulation : le client MUST envoyer `notifications/cancelled`. Le serveur SHOULD arrêter le travail et **MUST NOT send any further messages for it** (`:76-83`), ce qui est plus strict que 2025-11-25 (« SHOULD NOT send a response »).
- Arrêt : le serveur SHOULD sortir rapidement sur EOF de stdin (`:102-104`). Claude Code envoie SIGINT puis SIGTERM après 100 ms, puis SIGKILL après 400 ms supplémentaires (macOS/Linux) (https://code.claude.com/docs/en/mcp, WebFetch 2026-10-15). L'arrêt doit donc être quasi immédiat.
- Redémarrage : le protocole étant sans état, les requêtes en vol sont perdues et rejouables (`:109-115`).
- Les transports custom sur flux d'octets (UDS, TCP) SHOULD réutiliser ce framing (`:23-31` ; `SPEC/basic/transports/index.mdx:73-79`).
- **Conséquence pratique de la sonde.** Claude Code ≥ 2.1.292 sonde les serveurs stdio en 2026-07-28 par défaut (`[CC] CHANGELOG.md:652`). La note de la 2.1.238, « Fixed stdio MCP servers receiving a `server/discover` request before `initialize`, forcing lazy servers to start their backend on every session open » (`[CC] CHANGELOG.md:3400`), montre que la sonde peut forcer l'initialisation de tout le backend. Le SDK TypeScript lance la sonde dans un **processus frère éphémère** pour `StdioClientTransport`, car « some stdio servers exit on any pre-`initialize` request (servers built on the official Rust SDK, rmcp, behave this way) » (`[TS] docs/protocol-versions.md:108`). Il faut donc :
  1. démarrer très vite, sans appel réseau (pas d'OAuth PISTE au démarrage) ;
  2. répondre à `server/discover` à partir de données statiques ;
  3. ne jamais quitter le processus sur une méthode inattendue.
  - Le délai de sonde de Claude Code est inconnu. Un tiers cite « 3 s » (**NON VÉRIFIÉ**, résultat de recherche sur la PR YawLabs/mcp#198). Le SDK TS prend par défaut le timeout de requête (`[TS] docs/protocol-versions.md:94`).

### 5.2 Streamable HTTP (phase 2)

Changements de forme (`SPEC/basic/transports/streamable-http.mdx:14-25`) : **plus d'endpoint GET**, plus de sessions.

## 6. Tools

### 6.1 Ce qui change ou est précisé

- Capacité `tools{listChanged?}` (`SPEC/server/tools.mdx:45-60`). La liste MUST NOT varier par connexion ou par effet de bord ; elle MAY varier selon l'autorisation présentée (`:62-69`). Ordre déterministe SHOULD (`:71-74`).
- `tools/list` : pagination et **cache** (`:78-81`). Exemple avec `nextCursor`, `ttlMs: 300000`, `cacheScope: "public"`.
- Type `Tool` (`SCHEMA:1973-2015`) : `name`, `title?`, `description?`, `icons?`, `inputSchema` (**`type: "object"` requis à la racine**, tout mot-clé 2020-12 permis), `outputSchema?` (tout JSON Schema 2020-12), `annotations?`, `_meta?`. Ordre d'affichage du nom : `title`, puis `annotations.title`, puis `name` (`SCHEMA:2010`). **`execution` a disparu** (comparer `[S] schema/2025-11-25/schema.ts:1270`).
- Sans paramètre : `{ "type": "object", "additionalProperties": false }` recommandé (`SPEC/server/tools.mdx:293-296`).
- Noms : 1 à 128 caractères, `[A-Za-z0-9_.-]`, sensibles à la casse, uniques (SHOULD) (`:309-321`). Côté Claude Code, le nom complet `mcp__<server>__<tool>` doit tenir en 128 caractères, faute de quoi le tool est écarté (https://code.claude.com/docs/en/mcp).
- `ToolAnnotations` inchangées (`SCHEMA:1912-1954`) : `title`, `readOnlyHint` (défaut false), `destructiveHint` (défaut true), `idempotentHint` (défaut false), `openWorldHint` (défaut true). Le client MUST les considérer comme non fiables si le serveur ne l'est pas (`SPEC/server/tools.mdx:304-307`). Un billet de blog officiel recommande `readOnlyHint: true` pour les tools en lecture et `openWorldHint: false` pour les domaines fermés (`[S] blog/content/posts/2026-03-16-tool-annotations.md:141`).
- Résultat (`SCHEMA:1809-1838`) : `content: ContentBlock[]` (requis), `structuredContent?: unknown` (**toute valeur JSON**, auparavant objet uniquement : `[S] schema/2025-11-25/schema.ts:1113`), `isError?`. Avec un `outputSchema`, le serveur **MUST** fournir un `structuredContent` conforme (`SPEC/server/tools.mdx:509-515`) et SHOULD dupliquer le JSON sérialisé dans un `TextContent` (`:500`).
- Erreurs (`:738-785`) :
  - erreurs de protocole (tool inconnu, requête mal formée) → JSON-RPC, l'exemple utilise `-32602` « Unknown tool » ;
  - erreurs d'exécution (échec d'API, **validation d'entrée**, logique métier) → `isError: true` dans le résultat.
- Sécurité : le serveur **MUST** valider les entrées, contrôler les accès, **limiter le débit** des invocations et assainir les sorties (`:787-794`).
- « Stateful tools » (non normatif, `:683-736`) : handles explicites, opaques, à durée de vie annoncée, avec une erreur d'exécution claire à expiration. Pour nous, c'est pertinent si l'on expose un curseur de résultats de recherche Légifrance comme handle.
- `listChanged` : notification uniquement sur un flux `subscriptions/listen` avec `toolsListChanged: true` (`:236-248`).
- **Pas de pagination interne obligatoire** : un serveur de 8 à 13 tools peut tout renvoyer sans `nextCursor`. Le curseur invalide → `-32602` (`SPEC/server/utilities/pagination.mdx:109-111`).

### 6.2 Recommandations de schéma compatibles avec les deux ères

La révision 2025-11-25 imposait `outputSchema.type = "object"` et `structuredContent` objet (`[S] schema/2025-11-25/schema.ts:1279-1284`, `:1113`). Pour servir les deux ères avec **une seule définition** :

- `outputSchema` toujours à racine `"type":"object"` ; envelopper les listes, par exemple `{ "results": [...], "total": n }`.
- `inputSchema` sans combinateur à la racine (`anyOf`/`oneOf`/`allOf`). L'API Claude ne les accepte pas à la racine, Claude Code les aplatit ou écarte le tool (https://code.claude.com/docs/en/mcp, section « Tool input schemas with a root-level combinator »). Noms de propriétés de premier niveau : 1 à 64 caractères `[A-Za-z0-9_.-]` (même page, « Tools with invalid input schemas »).
- Pas de `$ref` externe (`SPEC/basic/index.mdx:299-310`). `$defs` locaux tolérés mais à éviter.
- Toujours doubler `structuredContent` d'un bloc texte lisible. Beaucoup de clients n'exposent que `content` au modèle, comme l'indique la feuille de route : « a server developer today has no way to know which form a given client will put in front of the model » (`[S] blog/content/posts/2026-08-22-mcp-roadmap.md:65`).
- Annotations pour Légifrance : `readOnlyHint: true`, `destructiveHint: false`, `idempotentHint: true`. Pour `openWorldHint`, voir les questions ouvertes.

## 7. Resources, templates, completions, prompts, logging, progress, cancellation, subscriptions, tasks

### 7.1 Caching (nouveau, SEP-2549)

- Opérations qui **DOIVENT** porter `ttlMs` et `cacheScope` sur les résultats `complete` : `server/discover`, `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list`, `resources/read` (`SPEC/server/utilities/caching.mdx:13-21`).
  - Le changelog n'en cite que cinq (`SPEC/changelog.mdx:36`), sans `server/discover`. Mais `DiscoverResult extends CacheableResult` (`SCHEMA:678`) : il faut donc l'inclure aussi.
- Les résultats `input_required` ne sont pas cachables (`:23-25`). Les retries MRTR MUST NOT être cachés (`:34-37`).
- `ttlMs` est un entier supérieur ou égal à 0 (MUST) (`:60`). `0` signifie immédiatement périmé (`:52-53`).
- `cacheScope` : `"public"` (aucune donnée propre à l'utilisateur, partageable par des proxys) ou `"private"` (lié au contexte d'autorisation) (`:93-108`).
- Même `cacheScope` sur toutes les pages d'une liste (MUST) (`:166-169`).
- Ne jamais s'en remettre à `cacheScope` pour le contrôle d'accès (MUST) (`:171-179`).
- Par défaut, le SDK TS émet `ttlMs: 0, cacheScope: "private"`, la politique la plus prudente. Les réponses 2025 ne portent **jamais** ces champs (`[TS] docs/migration/support-2026-07-28.md:687-694`).
- Proposition pour Légifrance :
  - `server/discover`, `tools/list`, `prompts/list` et `resources/templates/list` : `public`, TTL long (1 h à 24 h), puisque le contenu est statique par build ;
  - `resources/read` sur un texte juridique : `public` (données publiques identiques pour tous), TTL modéré.

### 7.2 Resources et resource templates

- Capacité `resources{subscribe?, listChanged?}` ; `{}` si aucune des deux (`SPEC/server/resources.mdx:39-72`). La liste MUST NOT varier par connexion (`:74-81`).
- `resources/read` peut renvoyer plusieurs `contents` et un `InputRequiredResult` (MRTR) (`:173-177`). `ReadResourceResult extends CacheableResult` (`SCHEMA:1229-1231`).
- `resources/templates/list` : RFC 6570, pagination et cache (`SPEC/server/resources.mdx:181-230`). Arguments complétables via `completion/complete` avec `ref/resource` (`:184-185`).
- Schémas d'URI : un schéma custom MUST respecter la RFC 3986 (`:397-400`). `https://` SHOULD être réservé aux ressources que le client peut récupérer lui-même (`:371-381`). Pour nous : `legifrance://…`.
- Erreurs : ressource inexistante → **MUST `-32602`** (`:404-405`). Les clients SHOULD encore accepter `-32002` (`:407-408`). Le serveur MUST NOT renvoyer un tableau `contents` vide pour une ressource inexistante (`:410`).
- Sécurité : le serveur MUST valider les URI (`:430`).
- Annotations (`audience`, `priority`, `lastModified`) disponibles sur les ressources, templates et blocs de contenu (`:336-364`). `lastModified` est utile pour la date de version d'un article.

### 7.3 Prompts

- Capacité `prompts{listChanged?}`, déclarée dans `DiscoverResult` (`SPEC/server/prompts.mdx:39-55`). Liste MUST NOT varier par connexion (`:57-64`). `prompts/list` paginé et cachable (`:68-120`).
- `prompts/get` : `arguments` de type `{[k]: string}` (`SCHEMA:1602-1611`) ; peut renvoyer `InputRequiredResult` (`SPEC/server/prompts.mdx:165`). `GetPromptResult` n'est **pas** cachable (`SCHEMA:1634-1640`).
- Erreurs : nom invalide ou argument requis manquant → `-32602` (`SPEC/server/prompts.mdx:319-325`).

### 7.4 Completions

- Capacité `completions: {}` (`SPEC/server/utilities/completion.mdx:33-42`). Inchangé hormis `resultType` et `_meta`.
- Au plus **100 valeurs** par réponse ; `total` et `hasMore` optionnels (`:142-147`).
- Références `ref/prompt` (par `name`) et `ref/resource` (par `uri` ou URI template) (`:133-140`).
- `context.arguments` transmet les arguments déjà résolus (`:89-114`).
- Erreurs `-32601`, `-32602`, `-32603` (`:185-192`). Limitation de débit MUST (`:207-213`).

### 7.5 Logging (déprécié) et Progress

- Logging déprécié (`SPEC/server/utilities/logging.mdx:7-18`) : les nouvelles implémentations SHOULD NOT l'adopter et doivent journaliser sur stderr (stdio) ou via OpenTelemetry.
  - Si on le gardait : capacité `logging`, niveau par requête via `_meta.logLevel`, MUST NOT émettre sans cette clé, `notifications/message` uniquement sur le flux de la requête (`:58-72`).
  - **Décision recommandée :** ne pas déclarer `logging`, et utiliser `tracing` vers stderr.
- Progress (`SPEC/basic/patterns/progress.mdx`) :
  - `progressToken` dans `_meta` (`:13-18`) ;
  - `progress` MUST croître (`:53-55`) ;
  - uniquement pour une requête active (`:60-62`), et MUST s'arrêter à la complétion (`:90`) ;
  - le serveur MAY n'en envoyer aucun.
  - Utile pour des recherches longues ou une pagination amont, et facultatif.

### 7.6 Cancellation et `subscriptions/listen`

- Annulation (`SPEC/basic/patterns/cancellation.mdx`) : stdio → `notifications/cancelled` du client ; HTTP → fermeture du flux (`:35-43`). Ignorer les annulations invalides (`:111-120`). Gérer les courses (`:84-104`).
- `subscriptions/listen` (`SPEC/basic/patterns/subscriptions.mdx`) :
  - filtre `toolsListChanged`, `promptsListChanged`, `resourcesListChanged`, `resourceSubscriptions[]` (`:40-50`) ;
  - le serveur MUST NOT envoyer un type non demandé (`:14-16`) ;
  - le serveur MUST envoyer `notifications/subscriptions/acknowledged` comme **premier** message portant le `subscriptionId`, avec le sous-ensemble honoré, les types non supportés étant omis (`:52-62`) ;
  - chaque notification MUST porter `io.modelcontextprotocol/subscriptionId`, égal à l'`id` JSON-RPC de la requête listen (`:83-92` ; `SPEC/basic/index.mdx:412-414`) ;
  - fermeture gracieuse : réponse `resultType: "complete"` avec `_meta.subscriptionId` (SHOULD) (`:128-158`) ;
  - sur stdio, après reconnexion, le client MUST ré-émettre la requête (`:160-162`).
- **Exigence minimale pour nous.** `SPEC/basic/index.mdx:17-19` impose que « All implementations **MUST** support the base protocol, versioning, and the message patterns », et Subscribe/Notify est l'un de ces patterns (`SPEC/basic/patterns/index.mdx`). La conformance vérifie l'ack en premier message (`[CF] src/scenarios/server/stateless.ts:51-53`, `:990`). Avec des listes statiques, l'implémentation minimale consiste à :
  1. renvoyer l'ack avec `notifications: {}` ;
  2. garder le flux ouvert jusqu'à annulation, EOF ou fermeture du flux HTTP ;
  3. à l'arrêt, envoyer la réponse de clôture gracieuse.
  - L'Inspector affiche « Not acknowledged » si le serveur répond par un simple résultat sans ack (`[S] docs/docs/2026-07-28/tools/inspector/protocol-eras.mdx`, section Resource subscriptions).

### 7.7 Tasks

- Les tâches sortent du cœur (`SPEC/changelog.mdx:22`) et deviennent l'extension `io.modelcontextprotocol/tasks` (`[S] docs/extensions/tasks/overview.mdx:50-73`). Le serveur décide de créer une tâche et renvoie `resultType: "task"`. Le client poursuit avec `tasks/get`, `tasks/update` et `tasks/cancel`. `tasks/list` est supprimé (`[S] blog/content/posts/2026-05-21-mcp-2026-07-28-rc.md:220-226`).
- Le serveur ne doit jamais renvoyer de tâche à un client qui n'a pas déclaré l'extension (`[S] docs/extensions/tasks/overview.mdx:229-234`).
- **Inutile pour nous** : appels Légifrance courts et synchrones.

## 8. Multi Round-Trip Requests (MRTR)

- Principe : au lieu d'émettre `elicitation/create`, `sampling/createMessage` ou `roots/list`, le serveur répond par un `InputRequiredResult` (`resultType: "input_required"`). Ce résultat contient `inputRequests` (une map de requêtes) et/ou `requestState` (un blob opaque). Le client ré-émet la **même** requête avec un **nouvel `id`**, `inputResponses` et le `requestState` renvoyé à l'identique (`SPEC/basic/patterns/mrtr.mdx:25-52`, `:124-131` ; `SCHEMA:537-609`).
- Requêtes concernées : **uniquement** `tools/call`, `resources/read` et `prompts/get`. Interdit ailleurs (MUST NOT) (`SPEC/basic/patterns/mrtr.mdx:182-192`).
- Exigences serveur (`:224-247`) :
  - au moins un des deux champs `inputRequests` ou `requestState` (MUST) ;
  - jamais une `inputRequest` d'un type que le client n'a pas déclaré (MUST NOT) ;
  - `requestState` est une **entrée contrôlée par l'attaquant**, à protéger en intégrité (HMAC ou AEAD) s'il influence l'autorisation ou la logique (MUST) ;
  - anti-rejeu SHOULD : principal, TTL court, empreinte de la requête d'origine ;
  - ne jamais supposer que le client répondra.
- Gestion des erreurs : information manquante → SHOULD renvoyer un nouvel `InputRequiredResult` plutôt qu'une erreur (`:259-267`).
- Attention : l'exemple du billet RC (`"type": "elicitation"`, `"schema"`) n'a **pas** la forme normative. La forme finale est `{"method":"elicitation/create","params":{...}}` (`[S] blog/content/posts/2026-05-21-mcp-2026-07-28-rc.md:146-158` à comparer avec `SPEC/basic/patterns/mrtr.mdx:58-80`).
- **Pour un serveur Légifrance en lecture seule.**
  - Sampling et Roots sont dépréciés (§10), donc à exclure.
  - L'élicitation pourrait servir à faire choisir l'utilisateur entre plusieurs textes ambigus (homonymie de codes), ou à confirmer une requête coûteuse. Il vaut mieux renvoyer les candidats au modèle dans le résultat du tool.
  - Les identifiants PISTE sont des **secrets** : la spec interdit de les demander en mode formulaire (`SPEC/client/elicitation.mdx:30-32`). En stdio, l'authentification SHOULD venir de l'environnement (`SPEC/basic/index.mdx:221-226`).
  - **Conclusion : ne pas implémenter MRTR en v1.** Il faut toutefois que les désérialiseurs acceptent la présence des champs `inputResponses` et `requestState` dans `CallToolRequestParams`, `ReadResourceRequestParams` et `GetPromptRequestParams` (`SCHEMA:600-609`, `:1205-1206`, `:1602`, `:1863`) sans planter. Le serveur ne renvoie jamais `input_required`.
  - En mode legacy, les SDK proposent un « shim » qui rejoue MRTR en vraies requêtes serveur → client (`[TS] docs/migration/support-2026-07-28.md:537-606`). Sans objet pour nous.

## 9. Framework d'extensions

- Déclaration : map `extensions` dans `ClientCapabilities` (par requête) et `ServerCapabilities` (dans `server/discover`). Clé = identifiant `{préfixe-vendeur}/{nom}` suivant les règles des clés `_meta`, **préfixe obligatoire**. Valeur = objet de réglages (`{}` = support sans réglage) (`SPEC/basic/versioning.mdx:80-119` ; `SCHEMA:785`, `:882`).
- Asymétrie : « the supporting party **MUST** either revert to core protocol behavior or reject the request with an appropriate error » (`SPEC/basic/versioning.mdx:121-124`). Les extensions sont désactivées par défaut (`[S] docs/extensions/overview.mdx:112-116`).
- Préfixes réservés : deuxième label `modelcontextprotocol` ou `mcp` (`SPEC/basic/index.mdx:337-339`). Une extension tierce utilise un DNS inversé qu'on possède (`[S] docs/extensions/overview.mdx:12-16`).
- Processus : SEP-2133, track « Extensions », dépôts `ext-*` (`[S] docs/extensions/overview.mdx:93-101` ; `[S] seps/2133-extensions.md`, statut Final).
- Extensions officielles (`[S] docs/extensions/client-matrix.mdx:26-31` ; `[S] docs/extensions/overview.mdx:22-75`) :

| Extension | Identifiant | Pertinence pour nous |
|---|---|---|
| MCP Apps | `io.modelcontextprotocol/ui` | Faible (UI HTML). Supportée par Claude web/Desktop, VS Code Copilot, ChatGPT, Cursor… (`client-matrix.mdx:37-47`) |
| OAuth Client Credentials | `io.modelcontextprotocol/oauth-client-credentials` | Possible pour un mode HTTP machine à machine |
| Enterprise-Managed Authorization | `io.modelcontextprotocol/enterprise-managed-authorization` | Hors périmètre |
| Skills over MCP | `io.modelcontextprotocol/skills` (SEP-2640 Final) | **Intéressante plus tard** : des « skills » de recherche juridique servies comme ressources. Exige la capacité `resources` + `skills/list` et `skills/get` (`[S] docs/extensions/skills/overview.mdx:50-75`). Support client encore partiel. |
| Tasks | `io.modelcontextprotocol/tasks` | Non |

- Côté Claude Code, des clés `_meta` propriétaires existent hors framework d'extensions : `anthropic/maxResultSizeChars`, `anthropic/alwaysLoad`, `anthropic/requiresUserInteraction` (https://code.claude.com/docs/en/mcp). `maxResultSizeChars` est utile pour les longs textes juridiques : seuil par défaut de 50 000 caractères, plafond de 500 000 (même page).

## 10. Autorisation (futur mode HTTP) : exigences 2026-07-28 côté resource server

Applicabilité : l'autorisation est **OPTIONNELLE**. En HTTP elle SHOULD suivre la spec. En stdio elle SHOULD NOT la suivre (identifiants pris dans l'environnement) (`SPEC/basic/authorization/index.mdx:18-24`).

Si l'on protège le mode HTTP :

1. **Le serveur MUST implémenter la Protected Resource Metadata (RFC 9728)** (`SPEC/basic/authorization/index.mdx:73-74`). Le document MUST contenir `authorization_servers` avec au moins un AS (`SPEC/basic/authorization/authorization-server-discovery.mdx:13-15`).
2. Découverte : `resource_metadata` dans `WWW-Authenticate` sur le 401 **ou** URI well-known, au chemin (`/.well-known/oauth-protected-resource/<chemin>`) ou à la racine (`authorization-server-discovery.mdx:39-47`).
3. `scope` dans le `WWW-Authenticate` : SHOULD (`SPEC/basic/authorization/index.mdx:99-114`).
4. Le serveur MUST valider le token selon OAuth 2.1 §5.2, MUST vérifier l'**audience** (RFC 8707). Un token invalide ou expiré MUST recevoir **401** (`:283-290`). Le serveur n'accepte que les tokens qui lui sont destinés (MUST) et MUST NOT accepter ni relayer d'autres tokens (`:294-297` ; `SPEC/basic/authorization/security-considerations.mdx:116-126`).
5. **Pas de passthrough** : si le serveur appelle une API amont (PISTE / Légifrance), il utilise **son propre** token amont et MUST NOT transmettre celui du client MCP (`security-considerations.mdx:126`). C'est déjà notre modèle (client OAuth PISTE côté serveur).
6. Statuts : 401 (non autorisé), 403 (scopes ou permissions insuffisants), 400 (requête d'autorisation mal formée) (`SPEC/basic/authorization/index.mdx:317-323`).
7. Scope insuffisant à l'exécution : SHOULD 403 + `WWW-Authenticate: Bearer error="insufficient_scope", scope="…", resource_metadata="…"` (`:332-343`). **Nouveau en 2026-07-28** : SHOULD inclure **tous** les scopes nécessaires dans un seul challenge ; pas d'obligation d'y remettre les scopes déjà accordés (`:344-359`). MUST tenir compte des hiérarchies de scopes (`:404-405`). Comparer avec 2025-11-25 : `[S] docs/specification/2025-11-25/basic/authorization.mdx:514-524`.
8. **Nouveau** : SHOULD NOT mettre `offline_access` dans le `scope` du `WWW-Authenticate` ni dans `scopes_supported` (`SPEC/basic/authorization/index.mdx:311-313`).
9. Sans session, **chaque requête** doit être authentifiée (`[S] seps/2575-stateless-mcp.md:692-696` ; « authorization **MUST** be included in every HTTP request », `SPEC/basic/authorization/index.mdx:269`). La liste de tools MAY dépendre des scopes (`SPEC/server/tools.mdx:66-69`). Dans ce cas, `cacheScope` doit être `"private"` (`SPEC/server/utilities/caching.mdx:105-108`).
10. Les autres durcissements de 2026-07-28 concernent le **client** ou l'**AS** : `iss` RFC 9207, `application_type`, liaison des identifiants à l'émetteur, dépréciation du DCR au profit de CIMD (`SPEC/changelog.mdx:38-48`, `:93-99`).

## 13. Incohérences et pièges relevés (à garder en tête)

1. **`server/discover` et le cache** : le changelog liste 5 opérations cachables (`SPEC/changelog.mdx:36`), la page Caching en liste 6 avec `server/discover` (`SPEC/server/utilities/caching.mdx:13-21`). Le schéma tranche : `DiscoverResult extends CacheableResult` (`SCHEMA:678`).
2. **Fin d'abonnement côté serveur** :
   - `SPEC/basic/patterns/cancellation.mdx:11-14` : « A server **MUST** send `notifications/cancelled` referencing a `subscriptions/listen` request ID when it tears down that subscription stream » ;
   - `SPEC/basic/patterns/subscriptions.mdx:122-136` : le serveur **SHOULD** envoyer une réponse de complétion ;
   - le schéma restreint l'envoi de `notifications/cancelled` par le serveur au **stdio** (`SCHEMA:637`).
   - Prudence : sur stdio, envoyer la réponse de complétion puis `notifications/cancelled` (**interprétation, NON VÉRIFIÉ** par une implémentation de référence).
3. **Mention résiduelle** « negotiated during initialization » à propos des extensions dans `SPEC/index.mdx:79-80`, contredite par le reste de la révision.
4. **Exemples des billets non normatifs** :
   - le billet GA et le billet RC montrent un `tools/call` dont le `_meta` ne contient que `clientInfo`, sans `protocolVersion` ni `clientCapabilities` requis (`[S] blog/content/posts/2026-07-28-spec-ga/index.md:47-56` ; `2026-05-21-mcp-2026-07-28-rc.md:80-90`). Un serveur conforme doit **rejeter** cette requête (`-32602`) ;
   - le JSON MRTR du billet RC n'a pas la forme finale (§8).
5. **Codes d'erreur de SEP-2243** : le SEP mentionne encore `-32001` pour `HeaderMismatch` (`[S] seps/2243-http-standardization.md:685`). La spec finale utilise `-32020` (`SPEC/changelog.mdx:61-67`).
6. **Libellé du champ `mimeType` des icônes** : légère différence entre `2026-07-28` et `draft` (`SPEC/basic/index.mdx:457`), sans impact.
7. **`supportedVersions` d'un serveur dual-era** : la spec ne dit pas s'il faut y lister des versions legacy. L'exemple de `-32022` liste `["2026-07-28","2025-11-25"]` (`SPEC/basic/versioning.mdx:62`), rmcp liste tout, le SDK TS seulement la version moderne. Voir les questions ouvertes.

## 15. Stratégie de compatibilité avec les clients 2025-11-25 / 2025-06-18 (/ 2025-03-26)

### 15.1 stdio : un processus, deux ères

L'algorithme de routage par message, appliqué avant toute logique métier, découle de `SPEC/basic/versioning.mdx:174-183`, de `SPEC/basic/transports/stdio.mdx:121-147` et du piège de conformance du §4.6 :

```
lire une ligne -> JSON
 ├─ tableau ? -> erreur -32600 (batch interdit)
 ├─ notification ?
 │    ├─ notifications/cancelled -> annuler la requête référencée (les deux ères)
 │    ├─ notifications/initialized -> marquer la session legacy prête
 │    └─ autre -> ignorer
 └─ requête
      ├─ params._meta["io.modelcontextprotocol/protocolVersion"] présent ?  => ÈRE MODERNE
      │     ├─ version ∉ {"2026-07-28"} -> -32022 {supported, requested}
      │     ├─ clientCapabilities absent -> -32602
      │     ├─ méthode ∈ {initialize, ping, logging/setLevel, resources/subscribe, resources/unsubscribe, …inconnue} -> -32601
      │     └─ dispatch sans état (résultats avec resultType, ttlMs/cacheScope, serverInfo en _meta)
      ├─ method == "initialize" (forme legacy : params.protocolVersion)  => ÈRE LEGACY pour ce processus
      │     └─ négocier : version demandée ∈ {2025-11-25, 2025-06-18, 2025-03-26} ? la renvoyer : renvoyer "2025-11-25"
      │        InitializeResult {protocolVersion, capabilities, serverInfo, instructions}
      ├─ session legacy établie ? -> dispatch legacy (ping -> {}, pas de resultType/ttlMs,
      │                              resource not found -> -32002, structuredContent objet)
      └─ sinon (requête sans _meta moderne, sans initialize préalable) -> -32602 « missing _meta »
         (le message SHOULD nommer les versions supportées, cf. versioning.mdx:154-157)
```

Points de décision :

1. **Versions legacy à accepter** : `2025-11-25` (cible, VS Code), `2025-06-18` (encore très répandue), `2025-03-26` en option. La négociation legacy suit l'ancienne règle : si la version demandée est supportée, la renvoyer telle quelle ; sinon renvoyer la plus récente supportée (`[S] docs/specification/2025-11-25/basic/lifecycle.mdx:167-172`).
2. **Formes de sortie selon l'ère** (« per-era wire codecs », approche du SDK TS : `[TS] docs/migration/support-2026-07-28.md:340-390`) :
   - en legacy, pas de `resultType`, pas de `ttlMs`/`cacheScope` (`[TS] …:687-694`) ;
   - code « resource not found » `-32002` pour les sessions legacy, `-32602` en moderne (rmcp fait de même : `[RS] crates/rmcp/src/model.rs:671`) ;
   - `icons` et `title` acceptables à partir de 2025-06-18 / 2025-11-25 ;
   - pas de `title` ni de `structuredContent` en 2025-03-26 (pas de `title` avant 2025-06-18 : `[S] docs/specification/2025-06-18/changelog.mdx:39-40`).
3. **Définitions de tools uniques**, valides dans les deux ères (§6.2) : racine `object` pour `inputSchema` et `outputSchema`, `structuredContent` objet.
4. **Capacités en legacy** : mêmes que dans `DiscoverResult`, sans `logging`, sans `listChanged`, sans `subscribe`. Le client legacy n'enverra alors ni `logging/setLevel` ni `resources/subscribe`. Si c'est le cas malgré tout → `-32601`.
5. **Pas de requête serveur → client**, même en legacy : aucune élicitation, aucun ping sortant.
6. **Coexistence** : la spec permet de servir les deux ères en même temps dans un même processus (`SPEC/basic/versioning.mdx:182-183`). Le SDK TS **épingle** l'ère par connexion selon l'échange d'ouverture (`[TS] docs/serving/legacy-clients.md:48-54`). Recommandation : accepter les requêtes modernes à tout moment, y compris après un `initialize` legacy. Une requête sans `_meta` moderne n'est acceptée qu'après `initialize`.
7. **Option de configuration** `--protocol-era {dual|modern|legacy}` (défaut `dual`), pour le diagnostic et pour suivre la fin du support legacy plus tard.

### 15.2 HTTP : un endpoint, deux ères

- Classification par requête, sur le **corps** puis les en-têtes. Un `initialize` legacy n'a ni `_meta` moderne ni, souvent, `MCP-Protocol-Version` (en 2025-06-18+, l'en-tête n'est requis qu'après l'initialisation : `[S] docs/specification/2025-06-18/changelog.mdx:29-30`).
- **Ère moderne** : toutes les validations du §14.2.
- **Ère legacy** : la recommandation est le mode « stateless legacy » à la manière du SDK TS (`legacy: 'stateless'`) : `initialize` est servi par une instance fraîche, sans `Mcp-Session-Id`, et GET/DELETE répondent 405 (`[TS] docs/serving/legacy-clients.md:8-40`). Cela suffit pour un serveur sans requête serveur → client ni notification non sollicitée. C'est conforme à 2025-11-25, où l'attribution d'une session est facultative : « A server using the Streamable HTTP transport **MAY** assign a session ID » (`[S] docs/specification/2025-11-25/basic/transports.mdx:198`).
- En-tête `MCP-Protocol-Version` absent sur une requête non-`initialize` : traiter comme `2025-03-26` seulement si l'on veut ces clients (`SPEC/basic/transports/streamable-http.mdx:277-281`). Sinon 400.
- Un client dual-era détecte un serveur moderne via un 400 avec corps d'erreur moderne (`:650-668`). Un `initialize` refusé doit donc renvoyer un corps JSON-RPC lisible ; inversement, le serveur ne doit pas renvoyer un 400 « moderne » sur un vrai `initialize` legacy.

### 15.3 Calendrier

- Rien n'oblige à retirer le legacy : le billet SDK précise que « nothing breaks on July 28 » et que la date marque seulement la publication du texte normatif (`[S] blog/content/posts/2026-06-29-sdk-betas-for-2026-07-28.md:42-47`).
- Les fonctionnalités dépréciées ne nous concernent pas : nous ne les utilisons pas.
- Critère proposé pour abandonner le legacy plus tard : support 2026-07-28 vérifié dans VS Code, Cursor et Claude Desktop.

## 17. Questions ouvertes

1. **`supportedVersions` d'un serveur dual-era** : y lister seulement `["2026-07-28"]` (comme le SDK TS) ou aussi les versions legacy (comme l'exemple `-32022` de la spec et rmcp) ? Et que faire d'une requête à enveloppe moderne qui porte `protocolVersion: "2025-11-25"` ? La spec ne tranche pas. La première option, plus prudente, renvoie `-32022` dans ce cas.
2. **`openWorldHint`** pour des tools qui interrogent l'API publique Légifrance (corpus fermé, mais service externe dont le contenu évolue) : `true` (valeur par défaut, « contenu potentiellement non fiable ») ou `false` (« domaine fermé ») ?
3. **Fin d'un `subscriptions/listen` sur stdio** : réponse de complétion, `notifications/cancelled` ou les deux (incohérence §13.2) ? Et faut-il garder ouvert un flux qui n'honore rien, ou le clore aussitôt après l'ack ?
4. **TTL de `resources/read`** pour des textes juridiques versionnés : quelle valeur (1 h ? 24 h ?) au regard des mises à jour quotidiennes de Légifrance ?
5. **Versions legacy à garder** : `2025-11-25` et `2025-06-18` suffisent-elles, ou faut-il aussi `2025-03-26` (sans `title` ni `structuredContent`) ?
6. **Clés `_meta` propriétaires de Claude Code** (`anthropic/maxResultSizeChars`, etc.) : les émettre pour les longs textes, au prix d'un couplage à un client ?
7. **Extension Skills** (`io.modelcontextprotocol/skills`) : piste pour une v2 du serveur (méthodes de recherche juridique servies comme skills), à réévaluer selon le support des clients.
